## v1.0.5 设计补充（2026-08-03）

> 这份记的是 v1.0.5 的**设计推理**——为什么这几条改动是自洽的、以及一条被 review 钉死的"没修干净"的诚实交代。
> CHANGELOG 只记"改了什么 + 诚实上限"；推理过程放这里。

### 一条贯穿的设计：痛点1 和 痛点2 是同一个机制的两面

v1.0.4 有个没被作者点破的**内部矛盾**：
- 铁律8 + 到底判据，逼模型往深推、**出跨域迁移题**验证用户懂没懂；
- 但用户**自己**在挖的过程中冒出的"那换场景会怎样"（本质就是一道跨域迁移题），却被第4步当中断处理、丢进 pending。

一边费力生产迁移题，一边把用户白送的迁移题扔掉——这是设计自相矛盾。

**v1.0.5 的解法是统一**：把"到底裁判用的底部验证题"和"用户中途冒的换场好奇"认成同一个东西的两种来源——
- sub-agent 预生成（结构化、防漏答案）；
- 用户当场冒出（自发、更真，但有考官腔风险）。

两种来源都喂进同一个"当场考一次"的机制。**统一的是机制、不是裁判权重**——用户题答出 ≠ 到底，预生成题才是最终裁判（见 SKILL.md 第2步）；钉这条边界，防止从本设计推出"用户题也算数"的误读。
这就是为什么 B 类接岔路不丢 pending、当场升级为正式迁移题——
**不是额外加功能，是堵掉 v1.0.4 的自相矛盾**。这条等价性是 v1.0.5 的核心设计洞，也是它敢说"同时碰两个痛点"的依据。

### review 钉死的"没修干净"：裁判链未终结

v1.0.5 把"到底判据"从"模型读三面红旗"**升级为"用户答底部验证题"为主裁判（三面红旗降级为辅助判据）**。表面看裁判从"自报"升级到了"客观"——
**但只升级了一半**：

```
v1.0.4:  模型读旗(自证)  →  判到底        ← 软
v1.0.5:  sub-agent 出题  →  用户答  →  判到底   ← 看着硬，但"出题硬不硬"没人裁判
```

题是 sub-agent 出的。题若软（换皮复述题冒充跨域迁移题），用户"答出"就什么都没证明。
**判定权没到客观物理，只是从"主模型读旗"转移到"sub-agent 出题质量"——问题换了位置，没消灭。**

这条 v1.0.5 **修不掉**，原因：题质量没有当场客观裁判（能想到的"再开一个 sub-agent 验题"会无限递归）。
唯一能验的是**独立测试者真跑、看题够不够硬**——而 v1 仍是 n=1，做不到。

所以诚实交代：v1.0.5 让"到底"比 v1.0.4 硬一截，但**离"真懂"还差两层**——
① 题质量保障（v1 做不到，gate 是独立测试）；② 跨天复验（v1.0.5 把机制接上了、地图还空、看不到收益）。
这条钉在 SKILL.md "已知局限"头条和 CHANGELOG 的诚实上限里，不假装解决。

### 为什么图膨胀用"插一挖一 + 封顶 2/轮"而不是别的

A 类前置缺口会动态往议程图插节点。风险：用户被迫多走无限节点，课程发散。

review 指出"收敛不靠铁律7"（铁律7管开放度不管图大小）——对。v1.0.5 的硬约束是经验拍脑袋：
- **插一挖一**：挖通那个前置就回主线，不在它里面再连锁插（防止前置套前置套前置）。
- **连锁封顶 2/轮**：第三个起的前置进 pending。

诚实说：**这两个数（1、2）没数据支撑**。可能 1 就够（更收敛），也可能该按目标大小弹性。
写进局限，等真人跑测校准——这是少就是多，不是定死。

### B 类为什么必须有红线

用户随口冒"那换场景呢"，模型立刻甩一道正式迁移题考他 = **变相考试**。
这是 07-02 纠正过的"被接住 vs 被曝光"那条老病，在 B 类上最容易复发。

v1.0.5 的红线不是新铁律，是**铁律5（撞墙即接住）+ 铁律7（信任门控）在 B 类上的具体落地**：
- 第一反应永远是先**接住好奇**（"问得好，这正是验证这定律的关键"），再递题；
- 低信任时**给脚手架**（搭桥 + 分两步问），别冷冰冰甩难题。

诚实补丁：协议文字管不住语气——模型语气一硬，红线就破。这是 v1.0.5 的**第一翻车点**，
得靠模型语用能力 + 真人反馈调，不是再写一条铁律能解决的。

# 设计补充 · v1.0.6（2026-08-10）

> 铁律 10 的两条等价性论证。真机实证触发：主 agent 没读源码就凭通用知识断言"代码怎么工作"，
> 被用户当场拆穿（"你根本没读过代码？刚才都在乱猜骗我？"）。

## 为什么"代码事实 = 信任根基"比"倒瀑布"更根本

铁律 1（永不倒瀑布）违反的后果是**信息密度问题**：一次给太多，用户吸收不了——可修复、可重讲，
伤害的是学习效率。铁律 10 违反的后果是**事实层面撒谎**：AI 讲的"代码怎么工作"是虚构的，用户
照此理解、迁移、甚至写进文档——伤害的是**学习体验的信任根基**（"AI 说的代码事实是真的"）。
效率问题可以容忍，信任崩坏不可逆。所以铁律 10 定性为"比倒瀑布更根本的失败模式"。

这条论证还解释了为什么"秒验抓手"（引用原文）是关键设计：模型自检不可靠（元认知局限），
协议文字管不住执行——唯一现实的反制是**让用户一秒能识破**。捏造的行号要跳转文件才能发现，
捏造的原文一眼假。防线从"用户较真追问"降到"用户扫一眼"。

## 为什么"对话回答例外"不破隐私铁则

隐私铁则禁止的是**落盘产物**（地图/pending/总结/报告）里的具体值——它们被持久化、被跨会话
复用、可能被误传。对话回答是**实时交互、不持久化**，路径+行号+原文片段只作为跳转/秒验的临时
抓手存在，用户看完就过去了。两个场景的泄漏风险差几个数量级，所以例外成立。

例外成立**不意味着放松**，配套三条护栏：
1. 路径优先相对路径，公司内部绝对路径默认抽象描述、仅用户明确要求才展示；
2. 原文含具体值（密钥/内部路径字面量）时对话里也用标注占位符（[密钥]）；
3. **例外仅适用主 agent 自己 Read/Grep 后的引用**——冷读 sub-agent 的输出仍绝对禁止带具体值
   （sub-agent 输出是"间接产物"，主 agent 无法预判其中每一处具体值，一票否决）。

护栏 3 是审出来的：第一版例外条款紧跟在"sub-agent 输出同样禁止带具体值"之后，弱模型可能把
例外误读成"对话回答里什么来源的内容都能带"。排除声明把两条规则的关系钉死：例外的主体
（主 agent 直接读）与禁止的主体（sub-agent 输出）不相交。
